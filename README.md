# FUSE GitHub — лабораторная по ОС

Учебная файловая система на **Python 3.12 + pyfuse3 + trio**, работающая с **настоящим GitHub REST API**. Вместо выполнения `git clone`, `git commit`, `git push` или сохранения копии репозитория на диск доступны обычные команды Linux: `ls`, `cat`, `mkdir`, `printf`, `rm`.

GitHub-репозитории отображаются как **ветки → коммиты → изменённые файлы**. Ветка также имеет `workspace/` с полным состоянием проекта и черновыми изменениями. `mkdir` под `_commit/` публикует отдельный неизменяемый Git-коммит, сохраняя остальные файлы репозитория.

## Файлы проекта

- `fuse_github.py` — обработчики FUSE, inode, виртуальное дерево, наложение рабочего состояния, создание веток/коммитов.
- `github_api.py` — **изолированный HTTP-модуль**, подготовленный с помощью LLM: GitHub REST API, авторизация, Git trees/blobs/commits/refs и HTTP-ошибки. Нет вызовов git CLI.
- `workspace_store.py` — атомарное локальное хранение черновиков в Base64 и контроль сохранения на диск.
- `tests/` — офлайн-тесты FUSE/HTTP с имитацией GitHub (не требуют сети и FUSE-монтирования).
- `smoke_test.sh` — команды реальной демонстрации с запросом подтверждения перед записью в репозиторий.

## Установка (Ubuntu 24.04)

Все команды этого раздела предполагают, что вы находитесь в корне скопированного или клонированного проекта, рядом с `fuse_github.py` и `requirements.txt`.

```bash
sudo apt update
sudo apt install -y python3-venv python3-dev build-essential pkg-config libfuse3-dev fuse3
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Для только чтения токен не требуется. Для **создания веток, работы в workspace и публикации коммитов** задайте переменную окружения **в терминале, в котором запускается FUSE**:

```bash
read -rs -p 'GitHub token: ' GITHUB_TOKEN; echo
export GITHUB_TOKEN
```

Создайте GitHub fine-grained personal access token с доступом **только к своему тестовому репозиторию** и разрешением `Contents: Read and write`. 

Запуск из каталога проекта:

```bash
python3 fuse_github.py --username YOUR_GITHUB_USERNAME --limit 10
```

Программа создаёт `./mnt` и монтирует файловую систему **без** глобального режима read-only. С другого терминала выполняются обычные команды. Для размонтирования:

```bash
mountpoint -q mnt && fusermount3 -u mnt
```

Локальные черновики и записи об успешно опубликованных коммитах хранятся отдельно для каждой комбинации GitHub-пользователя, репозитория и ветки. Это предотвращает смешивание изменений разных рабочих областей. Данные сохраняются на локальном диске вне точки монтирования FUSE, благодаря чему неопубликованные изменения не теряются после перезапуска файловой системы. Локальные файлы сохранены с правами `0600` (каталог `0700`).

## Дерево файловой системы

```text
mnt/
├── HELP.txt
└── sample-repo/
    ├── info.txt
    ├── README.md                
    └── branches/
        ├── main/
        │   ├── HEAD.txt
        │   ├── commits/
        │   │   ├── <full-sha>/
        │   │   │   ├── INFO.txt
        │   │   │   ├── CHANGES.txt
        │   │   │   ├── diff.patch
        │   │   │   └── changed/src/file.py
        │   │   └── pages/
        │   │       ├── 1/        # первая страница истории (до 30 коммитов)
        │   │       └── 2/        # появляется после полной первой страницы (30 SHA)
        │   ├── workspace/        # полный tree HEAD + неопубликованные изменения
        │   ├── _merge/                        # слияние опубликованной ветки
│   └── _commit/
        │       └── 001-my-change/
        │           └── SHA.txt
        └── feature%2Flogin/      # реальная GitHub-ветка feature/login
```

В `changed/` находятся **новые версии добавленных/изменённых файлов** только данного коммита (включая пути с вложенными каталогами). Удалённые файлы перечислены в `CHANGES.txt`, но не показываются в `changed/`. `diff.patch` загружается по запросу; API не гарантирует доступность больших и бинарных diff.

**Коммит — полный снимок Git tree, а не набор только изменённых файлов.** Каталог `changed/` — лишь удобное отображение отличий. При публикации новых изменений GitHub tree строится с `base_tree` исходного HEAD, затем поверх него накладываются новые blobs и tombstones.

Для merge-коммита показываются изменения относительно **первого родителя**. Слияние опубликованных веток выполняется через GitHub REST API; rebase не поддерживается.

## Создание новой ветки

```bash
mkdir mnt/sample-repo/branches/feature-demo
```

Это **сразу** создаёт на GitHub `refs/heads/feature-demo`, указывающую на SHA актуального HEAD **ветки по умолчанию** из метаданных репозитория (это не обязательно `main`). Ветки с `/` кодируются в отдельном компоненте пути:

```bash
mkdir mnt/sample-repo/branches/feature%2Flogin
# На GitHub: feature/login
```

Преобразование обратимое: `%` → `%25`, `/` → `%2F`, UTF-8 — percent encoding. Не надо создавать вложенные каталоги с именем `feature/login` непосредственно под `branches/`. 

## Подготовка и публикация изменений

```bash
cd mnt/sample-repo/branches/feature-demo/workspace
mkdir -p src
printf 'print("Hello FUSE!")\n' > src/hello.py
printf 'changed\n' > README.md
rm old.txt       # если файл действительно есть в проекте
# Пока ничего не отправлено на GitHub.

cd -  # вернуться в каталог проекта
mkdir mnt/sample-repo/branches/feature-demo/_commit/001-add-hello
cat mnt/sample-repo/branches/feature-demo/_commit/001-add-hello/SHA.txt
```

Именно команда `mkdir .../_commit/001-add-hello` создаёт Git blobs/tree/commit и обновляет ветку через GitHub API. Следующая команда `cat .../SHA.txt` только показывает SHA уже опубликованного коммита. Имя каталога `_commit/<label>` = **сообщение коммита** (уникальное среди созданных через этот mount/сохранённые receipts, до 80 символов UTF-8, не начинающееся с точки). Встроенного `git add` нет: **все** подготовленные изменения данной ветки включаются в один коммит. `mkdir _commit/002-empty` без изменений создаёт **пустой коммит** с тем же tree.

В уже опубликованных `commits/<sha>/` изменять или удалять файлы **нельзя**. Операции workspace выполняются локально; `rm` помечает удаление будущего Git tree, а не сразу удаляет файл из GitHub. `mkdir` пустого каталога workspace сохраняется локально, но Git сам по себе не хранит пустые директории.

## Слияние и удаление веток

Операции выполняются **на GitHub** с помощью `github_api.py`, без Git CLI. Для них требуется токен с правом `Contents: Read and write`.

Для слияния **опубликованных** изменений `feature-demo` в ветку `main`:

```bash
mkdir mnt/sample-repo/branches/main/_merge/feature-demo
cat mnt/sample-repo/branches/main/_merge/feature-demo/SHA.txt
```

Целевая ветка указана в пути **до** `_merge/`, исходная — **после** него. Если есть конфликты, GitHub возвращает HTTP 409 и операция отклоняется. Если у целевой ветки есть неопубликованные изменения в `workspace/`, merge не запускается. После успешного изменения HEAD целевой ветки требуется **размонтировать и снова запустить FUSE** перед дальнейшим редактированием этой ветки. В merge включены только уже опубликованные на GitHub коммиты, не локальные черновики.

Удаление ветки, отличной от ветки по умолчанию:

```bash
rmdir mnt/sample-repo/branches/feature-demo
```

Такой `rmdir` удаляет **GitHub-ветку**, а не обычную пустую папку. Ветка по умолчанию и ветки с неопубликованным локальным черновиком защищены от удаления. Локальные файлы состояния на диске автоматически не стираются.

## Если кто-то изменил ветку параллельно

При создании workspace запоминается `base_sha`. Перед публикацией HEAD запрашивается заново и сравнивается с `base_sha`. При расхождении FUSE возвращает `ESTALE` (может выглядеть как *Stale file handle*), пишет пояснение в терминал запуска, **не публикует** устаревший коммит и **сохраняет** черновик на диске. Перед передвижением ref HEAD проверяется повторно. `PATCH /git/refs` отправляется с `force:false`; GitHub не разрешает не-fast-forward даже при гонке между проверкой и обновлением.


## Кэш и ограничения учебной реализации

- Список репозиториев при запуске (1–30); ветки — лениво с TTL ~30 с; HEAD — TTL ~8 с. После записи локальный кэш обновляется. Внешние изменения рабочего состояния без локальных черновиков могут потребовать **размонтирования и нового запуска**.
- История — только первая страница 30 коммитов в `commits/`, следующие — `commits/pages/2`, `/3`, ... (до страницы 1000). Исторические объекты по SHA неизменяемы; история загружается по страницам.
- `workspace/` целиком перечисляет пути Git tree при **первом** входе, но содержимое конкретных файлов получает только при открытии/чтении; максимум **4000 элементов tree**, GitHub `truncated` → явная ошибка `EFBIG` (вместо тихой потери данных). `getattr` не выкачивает содержимое каждого файла.
- Отображение веток: первые **500 веток**. Если лимит достигнут, появляется `BRANCHES_LIMIT.txt`. UTF-8 имена веток отображаются однозначно, включая `/`.
- Чтение и запись обычных Git blobs: **до 2 МиБ на файл**, байты сохраняются без UTF-8 перекодирования; `100644` и `100755` поддерживаются. Symlink/submodule отображаются предупреждением, но не редактируются; Git LFS в API обычно представлен pointer-файлом, а не фактическим содержимым LFS.
- Переименования показываются в `CHANGES.txt` и новая версия по новому пути — в `changed/`; операции FUSE `rename` нет, поэтому перемещение файла в workspace следует делать через копирование и удаление. Нет force push и rebase. Merge опубликованных веток и удаление обычных веток поддерживаются.
- История коммита по GitHub API: до 3000 изменённых файлов; в `CHANGES.txt` выводится предупреждение, если лимит достигнут. Длинный diff может быть недоступен.
- Надёжность рассчитана на **одно монтирование** и **одного локального пользователя** для данного state-dir, без межпроцессных блокировок. Запись в черновик синхронно сохраняется через fsync + atomic rename; на ошибке файла возвращается ошибка. Для совместной работы несколькими локальными клиентами нужна дополнительная синхронизация.
- Отсутствует полная POSIX-совместимость (hard links, mmap/writeback, rename, xattrs, file locks и т.п.). Это учебный FUSE-адаптер GitHub, а не замена ext4 или Git CLI.

## Проверенные сценарии и документация

На Ubuntu были вручную подтверждены чтение репозиториев, веток и исторических версий файлов, операции `ADDED`, `MODIFIED` и `REMOVED`, создание ветки и нескольких коммитов на GitHub, сохранение черновика после перезапуска и отказ `ESTALE` при изменении удалённого HEAD. После исправления размера файла `changed/README.md` команды `stat` и `wc -c` показали **35 байт**; списки SHA в `commits/` и `pages/1` совпали, а несуществующая `pages/2` возвращала `ENOENT`. Сценарий истории **более 30 коммитов** и создание **пустого коммита** отдельно на реальном GitHub не подтверждены.

## Проверка без GitHub и FUSE

```bash
python3 -m unittest discover -s tests -v
python3 -m compileall -q fuse_github.py github_api.py workspace_store.py
```

Для реальной проверки нужен Ubuntu/Linux с `/dev/fuse`, пакеты `pyfuse3`, `trio`, сеть и **свой тестовый репозиторий**. Офлайн-тесты не подтверждают, что прямой GitHub-запрос на реальном сервере уже прошёл.

## Какие проверки показать преподавателю

1. `ls mnt` и `ls mnt/<repo>/branches` — настоящий FUSE и ветки GitHub.
2. `ls mnt/<repo>/branches/<branch>/commits` и `cat .../INFO.txt`, `CHANGES.txt`, `diff.patch`; `ls .../changed` — история и только изменённые пути.
3. `mkdir .../branches/feature-demo` — ветка появляется на GitHub без `git` CLI.
4. Создать/изменить/удалить несколько файлов в `workspace`; пока ещё нет изменений на GitHub.
5. `mkdir .../_commit/<label>` — GitHub HEAD меняется, появляются новые файлы, старые сохраняются; новый коммит отображается в FUSE.
6. `mkdir .../_commit/<new-label>` без файлов — пустой коммит.
7. Изменить HEAD ветки на GitHub извне и попытаться опубликовать локальный черновик — безопасный отказ, отсутствие force push и сохранение черновика.

В итоговом отчёте следует отдельно указать фактическое использование LLM при подготовке модуля `github_api.py` и описать ручное тестирование FUSE в Ubuntu, результаты которого приведены в [TESTING.md](docs/TESTING.md).
