# Архитектура файловой системы FUSE GitHub

Документ описывает архитектуру самостоятельного учебного проекта **FUSE GitHub**: пользовательскую файловую систему Linux с виртуальным представлением репозиториев, веток, истории коммитов и редактируемой рабочей области. Основные компоненты реализации — `fuse_github.py`, `github_api.py` и `workspace_store.py`. Описание ориентировано на изучение устройства системы и её принципов работы.

## 1. Назначение системы

Проект реализует пользовательскую файловую систему Linux на базе **FUSE** (`pyfuse3`), представляющую публичные репозитории GitHub в виде каталогов и файлов. Пользователь работает с обычными командами Linux, а приложение преобразует операции над виртуальной файловой системой в запросы к GitHub REST API либо в изменения локального черновика.

Система поддерживает чтение репозиториев, веток, истории коммитов и версий изменённых файлов, создание и удаление веток, слияние опубликованных веток, работу с файлами в `workspace/` и явную публикацию коммитов. Сами каталоги `mnt/<repo>/...` не являются клонированными Git-репозиториями.

## 2. Компоненты

| Компонент | Назначение |
|---|---|
| `fuse_github.py` | Точка входа; модель inode и узлов; реализация операций FUSE; виртуальное дерево; подготовка и публикация изменений. |
| `github_api.py` | Изолированный HTTP-адаптер GitHub REST API: получение данных, Git blobs/trees/commits/refs, авторизация и обработка HTTP-ошибок. |
| `workspace_store.py` | Локальное сохранение/загрузка черновиков рабочего пространства и квитанций об опубликованных коммитах. Используется через `WorkspaceStore` и `Draft`. |
| `.fuse_github_state/` | Каталог реального локального состояния **вне точки монтирования**. Не публикуется в репозитории. |
| `mnt/` | Точка монтирования виртуальной файловой системы; создаётся при запуске, не содержит исходный код. |
| `tests/` | Автоматизированные тесты; состав проверок определяется самими тестовыми файлами. |

`fuse_github.py` импортирует `GitHubAPI`, `GitHubAPIError`, `Draft`, `WorkspaceStore`. Сетевые запросы выполняются **только** через `github_api.py`.

## 3. Общая схема взаимодействия

```text
Команды пользователя: ls / cat / mkdir / echo / rm
                    |
                    v
               Ядро Linux
                    |
             интерфейс FUSE
                    |
                    v
          fuse_github.py (pyfuse3)
          |                     |
          | чтение / публикация | локальные правки
          v                     v
       github_api.py       workspace_store.py
          |                     |
          v                     v
     GitHub REST API      .fuse_github_state/
          |
          v
   Репозитории и Git-объекты GitHub
```

При `ls` и `cat` приложение обычно запрашивает информацию на GitHub и создаёт соответствующие виртуальные узлы. При редактировании `workspace/` изменения вначале сохраняются **локально**. Публикация происходит только при специальной операции `mkdir` внутри `_commit/`.

## 4. Модель виртуальных узлов и FUSE

В `fuse_github.py` используется структура `Node`. Каждый узел имеет уникальный `inode`, имя, родительский inode, тип (`kind`), признак каталога и при необходимости контекст репозитория, ветки, SHA коммита, путь файла, Git blob SHA, размер и содержимое. Таблица `nodes` хранит узлы по inode, а `children` — связи «родительский каталог → его элементы».

Основные обработчики:

| Обработчик | Роль в системе |
|---|---|
| `lookup` | Находит элемент по имени в каталоге, при необходимости лениво загружая его содержимое. |
| `getattr` | Возвращает метаданные узла: тип, права, размер, время, inode. |
| `opendir`, `readdir` | Открывают и перечисляют виртуальные каталоги. |
| `open`, `read` | Открывают файлы и читают содержимое из кэша, Git blob или других данных GitHub. |
| `create`, `write`, `setattr` | Создают и изменяют файлы **только** в рабочей области. |
| `unlink`, `rmdir` | Удаляют файлы/пустые каталоги из рабочей области; `rmdir` непосредственно под `branches/` удаляет GitHub-ветку. |
| `mkdir` | Создаёт ветку, локальный каталог, коммит через `_commit/` либо запускает слияние через `_merge/`. |
| `flush`, `fsync`, `release` | Обрабатывают операции над дескрипторами; сохранение правок выполняется при записи, а не только при закрытии файла. |

Исторические коммиты и их содержимое доступны для чтения, но не для изменения. Права виртуальных файлов также это отражают.

## 5. Ленивая загрузка и кэширование

Не всё дерево создаётся при монтировании. При первом входе в каталог соответствующий обработчик `_ensure_*` запрашивает необходимые данные и наполняет структуру `children`:

- `_ensure_branches`: список веток репозитория; кэш списка обновляется с интервалом около 30 секунд.
- `_ensure_branch`: служебные элементы ветки (`HEAD.txt`, `commits/`, `workspace/`, `_commit/`, `_merge/`).
- `_ensure_commits`, `_ensure_page`: загрузка истории страницами по **30 коммитов**.
- `_ensure_commit`: метаданные коммита, `CHANGES.txt`, `diff.patch` и дерево `changed/`.
- `_ensure_workspace`: построение рабочего состояния по Git tree исходного коммита с наложением локальных правок.
- `_ensure_changed_sizes`: при обращении к `changed/` подгружает из Git tree размеры изменённых файлов; содержимое каждого blob для этого загружать не нужно.

HEAD кэшируется на короткое время (в коде — около 8 секунд). **Перед публикацией** HEAD запрашивается заново, чтобы обнаруживать конфликты. Данные уже созданных узлов могут оставаться в памяти процесса; повторное монтирование полезно для полного обновления представления.

`commits/` и `commits/pages/1/` используют один и тот же набор SHA первой страницы истории. Последующие страницы становятся доступными последовательно по мере загрузки предыдущих; обращение к отсутствующей странице возвращает `ENOENT`. Если страница содержит ровно 30 записей, следующая страница может быть показана до фактического подтверждения наличия на ней коммитов.

## 6. Операции записи и локальный черновик

В рамках одного запуска для каждой пары «репозиторий — ветка» используется `BranchContext`: черновик `Draft`, блокировка операций этой ветки и исходное дерево файлов. На диске черновики разделены по тройке «GitHub-пользователь — репозиторий — ветка». Черновик связывается с **исходным SHA** (`base_sha`) — состоянием ветки, относительно которого выполняются локальные изменения.

Когда пользователь создаёт/редактирует/удаляет файл в `workspace/`:

1. Linux передаёт операцию FUSE-обработчику.
2. Обработчик определяет путь файла внутри ветки и проверяет право записи.
3. Изменение добавляется в локальный черновик (`edits`, а при необходимости — режим файла или информация о каталоге).
4. `WorkspaceStore.save(...)` сохраняет черновик вне `mnt/`.
5. Видимое содержимое `workspace/` обновляется, но удалённая ветка GitHub **ещё не изменяется**.

Это позволяет сохранять неопубликованные изменения между остановкой и повторным запуском FUSE.

## 7. Создание ветки

Операция `mkdir mnt/<repo>/branches/<branch>` вызывает создание Git reference `refs/heads/<branch>` от **HEAD ветки по умолчанию** данного репозитория. Это не создание пустого каталога на диске. Для обращения к веткам с `/` имя кодируется в одном компоненте пути, например `feature/login` → `feature%2Flogin`.

## 8. Публикация коммита

Команда:

```bash
mkdir 'mnt/<repo>/branches/<branch>/_commit/<message>'
```

запускает `_publish(...)`. Основные шаги:

1. Получить **актуальный** HEAD удалённой ветки и сравнить с `draft.base_sha`.
2. Если SHA различаются, вернуть `ESTALE` (*Stale file handle*) и оставить черновик локально.
3. Прочитать дерево текущего базового коммита.
4. Для изменённых/созданных файлов создать Git blobs; для удалённых файлов подготовить операции с `sha: null`.
5. Сформировать новое Git tree (при отсутствии операций возможно использование прежнего дерева).
6. Создать Git commit с указанным сообщением и родителем — прежним HEAD.
7. Повторно проверить HEAD и обновить ссылку ветки **без force push**.
8. При успешной публикации обновить локальное состояние, очистить применённые правки и создать виртуальную квитанцию `_commit/<message>/SHA.txt`.

Создание Git-объекта commit и продвижение ветки — разные операции: новый коммит считается опубликованным в ветке после успешного обновления ref. В случае сетевой ошибки необходимо проверять фактическое состояние GitHub, а не предполагать успех или неуспех только по одной ошибке клиента.

## 9. Слияние и удаление веток

В целевой ветке доступен служебный каталог `_merge/`. Операция `mkdir <target>/_merge/<source>` вызывает `POST /repos/{owner}/{repo}/merges`, где **base** — целевая ветка, а **head** — исходная. При успехе создаётся виртуальная квитанция `_merge/<source>/SHA.txt`. При конфликте GitHub возвращает HTTP 409; локальный алгоритм разрешения конфликтов не применяется. В слиянии участвуют только **опубликованные** изменения, а для целевой ветки с локальным черновиком операция запрещена. После успешного обновления целевой ветки программа требует повторного монтирования перед новой записью в неё, чтобы не редактировать устаревший снимок `workspace/`.

Удаление ветки выполняется `rmdir branches/<branch>`, которое вызывает `DELETE /repos/{owner}/{repo}/git/refs/heads/<branch>`. По умолчанию защищена главная ветка репозитория; наличие неопубликованного черновика или изменение HEAD с момента загрузки локального состояния также блокируют удаление. Удалённая GitHub-ветка исчезает из виртуального списка, но локальные данные состояния автоматически не удаляются.

## 10. Ограничения и безопасность

- Для записи требуется переменная окружения `GITHUB_TOKEN` и право **Contents: Read and write** для целевого репозитория; чтение публичных данных возможно и без токена с более строгими лимитами API.
- Максимальный размер одного обычного Git blob в лабораторной реализации — **2 МиБ**.
- Список публичных репозиториев при запуске ограничен **30**, список веток — **500**, размер дерева рабочего пространства — **4000 записей**. Большие/усечённые деревья не обрабатываются как обычное редактируемое workspace.
- Система не клонирует весь Git-репозиторий. Слияние опубликованных веток выполняет GitHub API, без локального `git merge`; не реализованы `rebase`, `push --force` и автоматическое разрешение конфликтов.
- Git LFS, символьные ссылки и Git submodules не представлены как обычные редактируемые файлы.
- В историческом `changed/` показываются **новые версии** добавленных/изменённых файлов; удалённые файлы указываются в `CHANGES.txt`, но не имеют содержимого в `changed/`.
- Исторические метаданные и diff могут требовать дополнительных запросов; при API-ошибках некоторые операции могут возвращать ошибку FUSE (`EIO`, `EACCES` и др.).
- Токены и `.fuse_github_state/` не должны попадать в публичный Git-репозиторий.

## 11. Использование LLM

Модуль `github_api.py`, содержащий интеграцию с GitHub REST API, подготовлен с использованием помощи LLM и отделён от реализации FUSE. Остальные компоненты обращаются к нему через методы `GitHubAPI`. Такое разделение позволяет независимо изучать сетевые запросы и логику файловой системы, а также тестировать их по отдельности.
