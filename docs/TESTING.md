# Тестирование файловой системы FUSE GitHub

Документ содержит результаты **ручного тестирования в Ubuntu**, порядок воспроизведения основных сценариев и перечень проверок, остающихся за рамками проведённых испытаний. Для чтения использовались публичные репозитории `tisak142/OPI` и `octocat/Hello-World`; операции записи выполнялись в тестовом репозитории `tisak142/fuse-lab-test`.

## 1. Среда и способ проверки

- ОС: Ubuntu в виртуальной машине; команды выполнялись во втором терминале при работающем процессе FUSE.
- Реализация: Python, `pyfuse3`, `trio`, GitHub REST API.
- Для чтения использовались публичные репозитории; для создания веток и коммитов — собственный тестовый репозиторий с токеном, имеющим разрешение `Contents: Read and write`.
- Проверки проводились на рабочем экземпляре файловой системы; фактические результаты приведены ниже. Размер исторических файлов сверялся через метаданные FUSE и чтение содержимого.

## 3. Примеры результатов команд

### Исторический README: различие одного байта

```bash
cat -A 553c2077f0edc3d5dc5d17262f6aa498e69d6f8e/changed/README
cat -A 762941318ee16e59dabbacb1b4049eec22f0d303/changed/README
```

Полученный вывод в одном терминале:

```text
Hello World!Hello World!$
```

`$` в `cat -A` обозначает конец строки. Первая версия не имеет перевода строки, поэтому следующий вывод начинается сразу после `!`.

### Удаление файла

```text
REMOVED hello.txt
```

Именно такой статус возвращается из GitHub API и переводится в верхний регистр. Для удаления содержимое файла в `changed/` отсутствует.

### Сохранение черновика после размонтирования

```text
$ cat mnt/fuse-lab-test/branches/feature-demo/workspace/draft.txt
Draft survives restart
```

### Отказ при конфликте

```text
mkdir: cannot create directory '.../_commit/conflict-test': Stale file handle
```

После отказа коммита `conflict-test` в истории ветки GitHub не было; `draft.txt` остался читаемым.

### Проверка размера файла

```text
Размер по метаданным: 35 байт
35
```

Первое значение получено из `stat`, второе — по содержимому через `wc -c`.

## 4. Рекомендуемый порядок демонстрации преподавателю

### A. Безопасное чтение (не меняет GitHub)

```bash
cd /путь/к/проекту
source .venv/bin/activate
python3 fuse_github.py --username octocat --limit 10
```

Во втором терминале:

```bash
ls mnt
ls mnt/Hello-World/branches
ls mnt/Hello-World/branches/master/commits
```

Для чтения коммита подставьте SHA из вывода `ls`:

```bash
sha=762941318ee16e59dabbacb1b4049eec22f0d303
base=mnt/Hello-World/branches/master/commits
cat "$base/$sha/INFO.txt"
cat "$base/$sha/CHANGES.txt"
cat "$base/$sha/changed/README"
```

### B. Проверка записи (изменяет ваш тестовый репозиторий)

После остановки первого запуска, размонтирования и установки токена запустите систему со своим аккаунтом. Выберите **новое уникальное имя тестовой ветки**, например `demo-check-01`:

```bash
repo=mnt/fuse-lab-test
branch=demo-check-01
mkdir "$repo/branches/$branch"
printf 'FUSE test\n' > "$repo/branches/$branch/workspace/check.txt"
cat "$repo/branches/$branch/workspace/check.txt"
mkdir "$repo/branches/$branch/_commit/demo-check-01"
cat "$repo/branches/$branch/_commit/demo-check-01/SHA.txt"
```

Затем проверьте новый коммит на GitHub. Эти команды **выполняют настоящую запись** в удалённый репозиторий.

### C. Проверка удаления (изменяет ваш тестовый репозиторий)

```bash
rm "$repo/branches/$branch/workspace/check.txt"
mkdir "$repo/branches/$branch/_commit/demo-remove-01"
```

После успешной публикации откройте `CHANGES.txt` нового SHA: там должна быть запись `REMOVED check.txt`.

## 5. Автоматические тесты

Если в опубликованном проекте присутствуют `tests/test_filesystem.py` и `tests/test_github_api.py`, выполните:

```bash
python3 -m unittest discover -s tests -v
```

Дополнительная быстрая проверка может запускаться скриптом:

```bash
bash smoke_test.sh
```

**Внимание:** перед запуском `smoke_test.sh` изучите его содержимое и проверьте целевой репозиторий: демонстрационный скрипт может выполнять операции записи на GitHub. В отчёте следует указывать фактический вывод запуска автоматических тестов, а не предполагаемое число успешных случаев.


## 6. Итог

Ручные проверки подтвердили основной пользовательский сценарий: **просмотр GitHub через FUSE → создание ветки → редактирование `workspace/` → публикация Git-коммита → восстановление черновика после перезапуска → защита от конфликтующего обновления HEAD**.
