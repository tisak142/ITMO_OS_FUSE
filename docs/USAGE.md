# Руководство пользователя FUSE GitHub

Все команды ниже выполняются **в Ubuntu/Linux**, где доступны FUSE 3 и `pyfuse3`. GitHub-репозиторий с исходным кодом при этом можно вести из Windows; саму FUSE-систему необходимо запускать в Linux.

> Примеры используют GitHub-пользователя `tisak142`, тестовый репозиторий `fuse-lab-test` и ветку `feature-demo`. Подставляйте свои значения. Операции записи выполняйте только в репозиториях, которыми управляете.

## 1. Установка

### Системные зависимости (Ubuntu)

```bash
sudo apt update
sudo apt install -y python3-venv python3-dev build-essential pkg-config libfuse3-dev fuse3
```

### Python-окружение

В каталоге проекта (там, где находятся `fuse_github.py` и `requirements.txt`):

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r requirements.txt
```

Виртуальное окружение создаётся один раз; `source .venv/bin/activate` нужно выполнять в каждом новом терминале, где требуются его пакеты. Для выхода: `deactivate`.

## 2. Токен GitHub

Публичные репозитории обычно можно просматривать без токена, но GitHub API применяет лимиты запросов. **Создание веток и коммитов требует** персонального токена (fine-grained) с доступом к соответствующему репозиторию и разрешением `Contents: Read and write`.

В терминале, в котором будет запущена FUSE:

```bash
read -rsp 'GitHub token: ' GITHUB_TOKEN
echo
export GITHUB_TOKEN
```

Ввод токена не отображается на экране. Проверить только факт наличия, **не выводя секрет**:

```bash
test -n "$GITHUB_TOKEN" && echo 'Token is set' || echo 'Token is missing'
```

**Не вставляйте токен в README, скриншоты, историю Git или публичные команды с открытым значением.** Токен из окружения FUSE-процесса не означает автоматическую авторизацию команды `git push` для публикации исходников.

## 3. Монтирование и размонтирование

Из каталога проекта:

```bash
source .venv/bin/activate
python3 fuse_github.py --username tisak142 --limit 30
```

Терминал с программой необходимо оставить открытым. По умолчанию точка монтирования — каталог `mnt/` рядом с `fuse_github.py`. Параметр `--limit` задаёт количество публичных репозиториев при запуске (от 1 до 30).

Во **втором терминале**:

```bash
cd /путь/к/каталогу/проекта
ls mnt
cat mnt/HELP.txt
```

Для остановки нажмите `Ctrl+C` в первом терминале; если монтирование сохранилось, выйдите из `mnt/` и размонтируйте:

```bash
cd /путь/к/каталогу/проекта
mountpoint -q mnt && fusermount3 -u mnt
```

Также доступны аргументы `--mountpoint` (другая точка монтирования) и `--state-dir` (другой каталог черновиков). **Каталог состояния должен располагаться вне точки монтирования.** Не удаляйте `.fuse_github_state/` при незавершённых изменениях.

## 4. Чтение репозиториев и веток

```bash
ls mnt
cat mnt/fuse-lab-test/info.txt
cat mnt/fuse-lab-test/README.md
ls mnt/fuse-lab-test/branches
cat mnt/fuse-lab-test/branches/main/HEAD.txt
```

Если имя ветки содержит `/`, замените разделитель на `%2F` при обращении к каталогу, например `feature/login` → `feature%2Flogin`.

## 5. Просмотр истории коммитов

```bash
base=mnt/fuse-lab-test/branches/main/commits
ls -1 "$base"
ls -1 "$base/pages/1"
```

Основной каталог `commits/` показывает первую страницу истории (до 30 SHA). Страница `pages/1/` представляет те же записи. Если у ветки есть следующая страница, она появляется в `pages/`:

```bash
ls -1 "$base/pages"
ls -1 "$base/pages/2"
```

`pages/2` может не существовать — это нормально при короткой истории. Страницы после первой загружаются последовательно, по мере перехода к ним.

Откройте один из SHA:

```bash
sha="ВСТАВЬ_SHA_ИЗ_ВЫВОДА_ls"
cat "$base/$sha/INFO.txt"
cat "$base/$sha/CHANGES.txt"
ls -la "$base/$sha/changed"
```

Вместо значения `ВСТАВЬ_SHA_ИЗ_ВЫВОДА_ls` используйте **реальный** 40-символьный SHA из вывода `ls`. Для чтения содержимого файла из конкретного коммита:

```bash
cat "$base/$sha/changed/README.md"
```

Такая команда работает, **только если README.md входит в изменения выбранного коммита**. Для удаления файл показывается в `CHANGES.txt` как `REMOVED`, но отсутствует в `changed/`.

Патч можно прочитать отдельно:

```bash
cat "$base/$sha/diff.patch"
```

При недоступности диффа файл может содержать диагностическое сообщение. Его размер в `ls -l` до первого чтения может отображаться как нулевой из-за ленивой загрузки.

## 6. Создание ветки через FUSE

Создание ветки производится **от текущего HEAD ветки по умолчанию** репозитория. Для тестирования используйте отдельный репозиторий, например `fuse-lab-test`:

```bash
mkdir mnt/fuse-lab-test/branches/feature-demo
ls mnt/fuse-lab-test/branches
```

После успеха ветку можно увидеть и на GitHub. Если `feature-demo` уже существует, выберите другое имя, например `feature-demo-2`.

## 7. Работа с `workspace/`

Путь к рабочей области:

```bash
ws=mnt/fuse-lab-test/branches/feature-demo/workspace
ls -la "$ws"
```

### Создание файла

```bash
printf 'Hello from FUSE!\n' > "$ws/hello.txt"
cat "$ws/hello.txt"
```

### Изменение существующего файла

```bash
printf 'Second version\n' > "$ws/hello.txt"
cat "$ws/hello.txt"
```

### Создание вложенного каталога и файла

```bash
mkdir "$ws/notes"
printf 'Draft note\n' > "$ws/notes/note.txt"
```

### Удаление файла

```bash
rm "$ws/notes/note.txt"
rmdir "$ws/notes"
```

Все эти действия изменяют **локальный черновик**. До создания коммита новые версии файлов могут отсутствовать на GitHub. Черновик сохраняется на реальном диске вне `mnt/` и рассчитан на переживание размонтирования.

## 8. Публикация коммита

Управляющая операция имеет вид:

```bash
mkdir mnt/fuse-lab-test/branches/feature-demo/_commit/my-first-commit
```

**Это не обычный каталог для файлов.** Его создание означает: опубликовать накопленные изменения ветки с указанным сообщением. Сообщение обязано быть новым для квитанций текущей ветки. При успешной публикации SHA можно прочитать так:

```bash
cat mnt/fuse-lab-test/branches/feature-demo/_commit/my-first-commit/SHA.txt
```

Для следующего коммита следует выбрать **другое** сообщение-каталог:

```bash
mkdir mnt/fuse-lab-test/branches/feature-demo/_commit/my-second-commit
```

Новый коммит появится в истории GitHub. После успешной публикации применённые локальные правки очищаются из черновика; рабочая область продолжает отражать состояние ветки.

## 9. Что делать при `Stale file handle`

Сообщение:

```text
mkdir: cannot create directory '.../_commit/conflict-test': Stale file handle
```

означает ошибку Linux `ESTALE`. В контексте публикации эта ошибка выдаётся, когда удалённый HEAD не совпадает с базовым SHA черновика либо обновление ссылки ветки не удалось по близкой причине.

Правильные действия:

1. **Не удаляйте** `.fuse_github_state/` и не пытайтесь многократно публиковать черновик вслепую.
2. Проверьте актуальную ветку и её историю на GitHub.
3. Сохраните копию изменённых файлов из `workspace/` в обычный каталог **вне `mnt/`**.
4. Вручную согласуйте изменения с актуальным состоянием удалённой ветки. Автоматического `merge` или `rebase` программа не выполняет.
5. Только после безопасного разрешения конфликта и проверки состояния черновика возобновляйте работу; при необходимости создайте свежую ветку.

При отказе от публикации черновик остаётся на локальном диске; он не очищается автоматически.

## 10. Тесты и диагностика

Проверить синтаксис главного модуля:

```bash
python3 -m py_compile fuse_github.py github_api.py workspace_store.py
```

Для запуска автоматизированных тестов из каталога `tests/`:

```bash
python3 -m unittest discover -s tests -v
```

Результат тестов зависит от текущего содержимого `tests/`; наличие тестовых файлов не гарантирует прохождения каждой проверки на любой машине.

Если команда над FUSE возвращает `Input/output error` или `Permission denied`, проверьте сообщения **первого терминала**, где запущен `fuse_github.py`: часть сетевых и внутренних ошибок логируется туда. Для диагностики полезны конкретный путь, команда, вывод и сообщения FUSE.
