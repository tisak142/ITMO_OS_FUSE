# Структура виртуальной файловой системы

Документ объясняет, **какие объекты видны в точке монтирования `mnt/`**, чем они отличаются от реальных файлов проекта и какие операции разрешены. Примеры соответствуют реализованной файловой системе FUSE GitHub.

## 1. Виртуальное дерево

```text
mnt/                                    ← точка монтирования FUSE
├── HELP.txt                             ← краткая справка
└── <repository>/                       ← один публичный репозиторий GitHub
    ├── info.txt                         ← сведения о репозитории
    ├── README.md                        ← README репозитория, если доступен
    └── branches/                        ← ветки репозитория
        └── <encoded-branch>/            ← одна ветка
            ├── HEAD.txt                 ← SHA текущего HEAD
            ├── workspace/               ← рабочая версия файлов + локальные правки
            │   └── ...                  ← структура файлов проекта
            ├── _commit/                 ← специальный каталог публикации
            │   └── <commit-message>/    ← квитанция о созданном коммите
            │       └── SHA.txt          ← SHA опубликованного коммита
            ├── _merge/                  ← управляющий каталог слияния
            │   └── <source-branch>/     ← квитанция о слиянии
            │       └── SHA.txt         ← SHA целевой ветки после слияния
            └── commits/                 ← история коммитов
                ├── <40-символьный-SHA>/  ← исторический коммит
                │   ├── INFO.txt         ← автор, дата, сообщение, родители
                │   ├── CHANGES.txt      ← ADDED, MODIFIED, REMOVED и другие статусы
                │   ├── diff.patch       ← diff коммита, если доступен через API
                │   └── changed/         ← содержимое изменённых файлов
                │       └── ...
                └── pages/               ← доступ к истории по страницам
                    ├── 1/               ← первые 30 коммитов
                    └── 2/               ← следующие 30 (если доступны)
```

Имена в угловых скобках — подстановочные значения, а не буквальные имена каталогов. `pages/2` и следующие страницы создаются по мере обнаружения дополнительной истории; **они не гарантированы** для любого репозитория.

## 2. Справочник каталогов и файлов

| Путь | Откуда берутся данные | Что разрешено |
|---|---|---|
| `mnt/HELP.txt` | Формируется приложением | Читать |
| `mnt/<repo>/` | Список репозиториев GitHub заданного пользователя | Открывать, перечислять |
| `info.txt` | Метаданные GitHub API | Читать |
| `README.md` (в корне репозитория) | GitHub README API или пояснение о недоступности | Читать |
| `branches/` | GitHub API: ветки | Перечислять; `mkdir` создаёт ветку, `rmdir` удаляет обычную ветку без черновика |
| `HEAD.txt` | GitHub ref `heads/<branch>` | Читать |
| `commits/` | GitHub API: история ветки | Читать |
| `commits/pages/N/` | N-я страница истории | Читать |
| `commits/<sha>/INFO.txt` | Данные коммита GitHub | Читать |
| `commits/<sha>/CHANGES.txt` | Список изменённых путей и статусов | Читать |
| `commits/<sha>/diff.patch` | Diff, полученный через GitHub API | Читать, если API предоставляет содержимое |
| `commits/<sha>/changed/` | Содержимое файлов, затронутых данным коммитом | Читать |
| `workspace/` | Файлы базового Git tree + локальный черновик | Читать, создавать, изменять, удалять |
| `_commit/` | Специальный управляющий каталог | `mkdir <сообщение>` публикует коммит |
| `_commit/<сообщение>/SHA.txt` | Сохранённая квитанция об успешной публикации | Читать |
| `_merge/` | Команда слияния удалённых веток | `mkdir <исходная-ветка>` выполняет merge |
| `_merge/<исходная-ветка>/SHA.txt` | SHA после слияния | Читать |

## 3. Особенности веток

Имя ветки Git может содержать `/`, а обычный путь Linux разделяет компоненты именно этим символом. Поэтому FUSE использует **обратимое кодирование имени ветки**:

```text
Имя Git-ветки:    feature/login
Имя каталога:     feature%2Flogin
```

При создании нового каталога в `branches/` приложение декодирует имя и выполняет запрос создания ветки от HEAD ветки по умолчанию. Недопустимые Git-имена отклоняются. Команда `rmdir branches/<ветка>` удаляет **удалённую GitHub-ветку**, если она не является веткой по умолчанию и не содержит неопубликованный локальный черновик.

## 4. Почему `commits/` и `pages/1/` содержат одинаковые SHA

`commits/` даёт быстрый доступ к первой странице истории без дополнительного уровня вложенности. `pages/1/` представляет **ту же самую первую страницу**, а `pages/2/`, `pages/3/` и следующие нужны для более старых коммитов.

Набор SHA первой страницы используется совместно для обоих каталогов. При истории короче 30 коммитов `pages/2` отсутствует, и попытка `ls pages/2` возвращает `No such file or directory`.

**Важно:** если первая страница содержит ровно 30 коммитов, наличие второго каталога ещё не доказывает существование 31-го коммита: это проверяется при загрузке второй страницы.

## 5. Что находится внутри каталога коммита

Пример:

```text
commits/<sha>/
├── INFO.txt
├── CHANGES.txt
├── diff.patch
└── changed/
    └── src/main/java/Example.java
```

`INFO.txt` содержит SHA, автора, дату, сообщение, родителей. У merge-коммита может быть несколько родителей. Список изменений берётся из GitHub API относительно первого родителя, что важно при интерпретации merge-коммитов.

`CHANGES.txt` содержит статусы из GitHub API в верхнем регистре:

```text
ADDED new.txt
MODIFIED README.md
REMOVED old.txt
```

Это **примеры статусов**, не содержимое одного конкретного коммита. В тестовом репозитории удаление `hello.txt` отобразилось как `REMOVED hello.txt`; это соответствует обозначению статуса, которое возвращает GitHub API.

`changed/` содержит **не полный снимок проекта**, а файлы из списка изменений, у которых существует новая версия. Например, для `MODIFIED README.md` доступна версия README из выбранного коммита. Для `REMOVED old.txt` файла `changed/old.txt` нет — удаление видно в `CHANGES.txt`.

История неизменяема: попытка редактировать файлы под `commits/<sha>/` не должна приниматься системой.

## 6. `workspace/` — рабочее состояние ветки

Этот каталог — пользовательский интерфейс редактирования. Он показывает файловое дерево базового коммита, поверх которого применены локальные изменения:

```text
workspace/
├── README.md       ← исходный файл ветки или локально изменённая версия
└── new-file.txt    ← новый файл, пока не опубликованный на GitHub
```

Физически содержимое не обязательно находится под настоящей папкой `mnt/.../workspace/`: путь виртуален. **Локальные изменения сохраняет `workspace_store.py` в `.fuse_github_state/` вне точки монтирования.** Не надо переносить этот каталог состояния в GitHub.

Обычные операции Linux над `workspace/`:

- `cat` — чтение файла;
- `echo ... > file` — создание либо перезапись;
- `mkdir workspace/subdir` — создание локального каталога;
- `rm workspace/file` — удаление файла в локальном черновике;
- `rmdir workspace/emptydir` — удаление пустого каталога.

Изменения появляются на GitHub **не при записи**, а только после публикации.

## 7. `_commit/` — не папка с историей, а команда

При выполнении:

```bash
mkdir mnt/<repo>/branches/<branch>/_commit/my-first-commit
```

обработчик FUSE запускает публикацию накопленного черновика с сообщением `my-first-commit`. При успехе внутри созданного управляющего каталога появляется `SHA.txt` с идентификатором коммита.

Имя сообщения должно быть новым для этой ветки в журнале квитанций; оно должно удовлетворять ограничениям реализации (длина 1–80 символов, без начальной точки, без разделителя пути). Для сообщения из нескольких слов можно использовать кавычки вокруг **всего пути**.

В случае изменения удалённого HEAD относительно сохранённой базы операция отклоняется с `Stale file handle` (`ESTALE`), а черновик сохраняется.

## 8. `_merge/` — слияние опубликованных веток

Для объединения опубликованных изменений исходной ветки с целевой используется:

```bash
mkdir mnt/<repo>/branches/main/_merge/feature-demo
cat mnt/<repo>/branches/main/_merge/feature-demo/SHA.txt
```

В этом примере `main` — целевая ветка, а `feature-demo` — исходная. Конфликтующие слияния отклоняются GitHub API; автоматического разрешения конфликтов нет. Локальные неопубликованные изменения не включаются в merge. После успешного изменения целевой ветки необходимо повторно смонтировать FUSE для корректного обновления её `workspace/`.

## 9. Что является настоящим файлом проекта, а что — виртуальным

**На реальном диске** находятся `fuse_github.py`, `github_api.py`, `workspace_store.py`, тесты, документы, `.fuse_github_state/` и каталог-точка монтирования `mnt/`.

**Виртуальными** являются содержимое `mnt/`, репозитории, ветки, каталоги коммитов, рабочее пространство и специальные служебные файлы. Они формируются программой и могут обращаться к сети при чтении. В репозиторий исходного кода включаются модули программы и документация, но не содержимое `mnt/` или `.fuse_github_state/`.
